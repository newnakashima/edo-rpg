# コードを検査する

このスキルは、指摘を洗い出して報告するところまでを受け持つ。コードの修正、コミット、プッシュは行わない。指摘をどう扱うかは、呼び出した側（ユーザーやほかのスキル）が決める。

## 指摘の重大さ

各指摘には、次のどれか 1 つの重大さを付ける。

- **P0（最重要）**：そのままでは出せない問題。データの破損や消失、セキュリティ上の欠陥、主要な機能が動かない、既存の挙動を壊す、ビルドやテストが通らない、など。
- **P1（重要）**：出す前に直すべき問題。ロジックの誤り、境界条件やエラー処理の漏れ、変更の目的を満たしていない点、変更した挙動に対するテストの不足、など。
- **P2（中〜軽微）**：直したほうがよいが、すぐに害が出るわけではない問題。明らかな重複や不要なコード、分かりにくくて誤解を招く名前や構造、起こりにくい条件での不具合、など。

迷ったときは、その問題が実際に起きる道筋（どの入力や操作で、何が起きるか）を具体的に書けるかで判断する。道筋を書けないものは、重大さを上げない。

書式や好みの問題は指摘しない。リポジトリの規約（CLAUDE.md、AGENTS.md、CONTRIBUTING.md など）に反している場合は、その規約を根拠として指摘してよい。

## 手順

### 1. 対象を決める

検査する変更を決め、その範囲を確かめる。

- 呼び出し側から範囲（コミット、ファイル、前回の検査からの変更分など）を指定された場合は、それに従う。起点はコミット ID で受け取るか、受け取った範囲をコミット ID に直して控える。
- 指定がなく PR が対象なら、PR 全体の差分とする。起点は次のように決める。
  1. base ブランチの名前を、呼び出し側の指定か `gh pr view --json baseRefName` で得る。どちらでも分からなければ、推測せずに止めて報告する。
  2. `git fetch origin <base>` で base を取得し直す。ローカルの `<base>` や `origin/<base>` が古いと、すでに base に入っている変更まで差分に混ざるためである。取得に失敗したら、古いまま進めずに止めて報告する。
  3. 起点を `git merge-base origin/<base> HEAD` で求め、そのコミット ID を控える。以後の差分は `git diff <起点のコミット ID> HEAD` で取り、ローカルのブランチ名や `origin/<base>` を直接使わない（`origin/<base>` の先頭を起点にすると、base 側に後から入った変更まで逆向きに混ざる）。
  4. 変更されたファイルの一覧（`git diff --name-only <起点のコミット ID> HEAD`）が、PR の変更ファイル（`gh pr view --json files`、または PR の画面）と一致するかを確かめる。一致しなければ、まずローカルの HEAD が PR の head（`gh pr view --json headRefOid`）と同じか、つまり未プッシュのコミットがないかを確かめる。そのうえで 2 からのやり直しを 1 回だけ試し、それでも一致しなければ、食い違うファイルを示して止めて報告する。`gh` も PR の画面も使えずに確かめられない場合は、その旨を報告に書く。
- 変更の目的（PR の説明、依頼内容、関連するタスク）が分かる場合は、それも集めておく。目的を満たしているかも検査の対象になる。
- 前回の検査の指摘を渡された場合は、それが直っているかも確かめる。

### 2. 観点ごとに検査する

軽量なサブエージェントを観点ごとに 1 つずつ起動し、並行して検査させる。観点は次を基本とし、変更の内容に応じて増減してよい（たとえば、テストやドキュメントだけの変更なら関係のない観点は省く）。

- **正しさ**：ロジックの誤り、境界条件、状態の扱い、並行性。
- **エラー処理**：失敗時の挙動、例外や異常値の扱い、後始末の漏れ。
- **セキュリティ**：認証・認可、入力の検証、秘密情報の扱い、インジェクション。
- **既存の挙動への影響**：呼び出し元や互換性を壊していないか、マイグレーションや設定の変更が漏れていないか。
- **テスト**：変更した挙動がテストされているか、テストが実際にその挙動を確かめているか。
- **重複と不要なコード**：既存の仕組みで済むものの作り直し、使われていないコード、残ったデバッグ用のコード。
- **目的との一致**：変更が目的を満たしているか、目的と関係のない変更が混ざっていないか。

各サブエージェントには、これまでの作業の文脈を渡さず、次のものだけを渡す。実装時の意図に引きずられず、差分そのものから判断させるためである。

- 検査する差分そのもの、または手順 1 で控えたコミット ID を使った取得方法（`git diff <起点のコミット ID> HEAD` など）。`origin/<base>` のように、サブエージェント側で指す先が変わりうる名前は渡さない。必要に応じて周辺のコードを読んでよいことも伝える。
- 担当する観点と、このスキルの「指摘の重大さ」の定義。
- 変更の目的（分かる場合）と、リポジトリの規約のありか。
- 報告の形式：指摘ごとに、場所（ファイルと行）、内容、問題が起きる道筋、重大さ、直し方の案。指摘がなければ「なし」と返すこと。

サブエージェントを使えない環境では、自分で観点ごとに順に検査する。その場合も、観点を 1 つずつ切り替えて差分を読み直す。

サブエージェントが失敗した、または決めた形式で返さなかった観点は、1 回だけ起動し直す。それでも結果が得られなければ、その観点は自分で検査する。どの観点も「指摘なし」と「検査できなかった」を混同しない。

### 3. 指摘を突き合わせる

すべてのサブエージェントの報告が集まったら、報告する前に指摘全体を見直す。

- **範囲を確かめる**：範囲の外のコードに触れる指摘は、次のどれにあたるかを見分ける。
  - 範囲に含まれない変更（差分にないはずのファイルの追加・削除・修正）を前提にしたもの：サブエージェントが別の差分を見ていた可能性が高い。取り下げ、控えたコミット ID を渡してその観点を検査し直す。これは「差分外の既存の問題」にも入れない。
  - 範囲内の変更が、範囲の外のコード（呼び出し元など）に影響するもの：通常の指摘として扱う。
  - 範囲内の変更と関係のない、もともとある問題：下の「確かめる」のとおり「差分外の既存の問題」として扱う。
- **確かめる**：各指摘について、該当するコードを自分で読み、問題が本当に起きるかを確かめる。起きないもの、差分と関係のない既存の問題は指摘の一覧から外す（既存の問題は、重大さを付けて「差分外の既存の問題」として別に報告する。P0 のものは必ず報告し、P1 と P2 は重要なものだけでよい）。
- **まとめる**：同じ問題を別の観点から指摘しているものは 1 件にまとめ、重大さは高いほうに合わせる。
- **見送り済みと照らし合わせる**：前回の見送り済みの指摘を渡された場合は、場所と内容が同じ指摘を見送り済みとして扱い、新しい指摘として数えない。ただし、重大さを付け直したもの（手順 4 を参照）は見送り済みとして扱わない。
- **重大さをそろえる**：観点ごとに基準がずれていないかを見て、「指摘の重大さ」の定義に照らして付け直す。
- **衝突を見つける**：直し方どうしが矛盾する指摘（片方を直すともう片方が悪化する、同じ箇所を別の形に変えようとしている、など）を探す。衝突する場合は、重大さの高いほうの直し方を優先する前提で、低いほうの指摘をその直し方と両立する形に改める。両立できない場合も指摘は取り下げず、両立できないことを書いて残す（どう扱うかは呼び出し側が決める）。重大さが同じで決められない場合は、要判断とする。
- **要判断を見分ける**：直し方が複数あって仕様や設計の選択が必要なもの、依頼内容と矛盾するものには、重大さとは別に「要判断」の印を付ける。

### 4. 報告する

次の形で報告する。

- 検査した範囲と、使った観点。
- 指摘の一覧。重大さの高い順（P0、P1、P2）に並べ、各指摘に次を含める。
  - 重大さと、要判断かどうか
  - 場所（ファイルと行）
  - 内容と、問題が起きる道筋
  - 直し方の案
  - ほかの指摘と衝突していた場合は、その相手と、どちらを優先したか（両立できない場合はその旨）
- 前回の指摘を渡された場合は、それぞれが直っているかどうか。見送り済みとして渡された指摘は「見送り済み」と書き、新しい指摘として数え直さない。ただし、その後の変更で該当箇所の挙動が変わっている場合は、今の差分に基づいて重大さを付け直し、その旨を書く。
- 差分外の既存の問題があれば、重大さを付けて、指摘の一覧とは分けて書く。
- 検査できなかった観点があれば、その観点と理由。
- 指摘がない場合は、その旨と、検査した範囲・観点。
