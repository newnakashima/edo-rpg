# PR のレビューからマージまで

## いつ始めるか

このスキルは作業の**最後**に行う仕上げの手順であり、作業の最初に行うものではない。

- 実装の依頼や、タスクを探して進めるスキルと一緒に指定された場合は、まずそちらに従ってタスクを決め、実装し、コミット・プッシュして PR を作成する。このスキルの手順 1 は、その PR ができてから始める。
- 現在のブランチにまだ PR がない、または実装が終わっていない場合は、レビューを始めない。既存の別の PR を探してレビューすることもしない。
- 指定されたのがこのスキルだけで、現在のブランチの PR が既にある場合は、そのまま手順 1 から始める。

## 前提

- GitHub CLI（`gh`）が使え、認証済みであること。
- 対象は現在のブランチの PR とする（`gh pr view --json number,url,baseRefName,headRefName` で確認する）。

## 手順

### 1. レビューする

code-inspection スキルを使って PR の差分を検査し、P0、P1、P2 の重大さ付きの指摘を受け取る。

- 2 回目以降は、前回からの変更分（前回検査したときの HEAD のコミット ID を起点にした範囲）と、前回の指摘（見送ったものを含む）を渡し、前回の指摘が直っているかも確かめてもらう。

指摘は重大さに応じて次のように扱う。

- **P0（critical）**：必ず修正する。ほかの指摘と直し方が衝突する場合は、P0 の直し方を優先する。
- **P1（serious）**：必ず修正する。
- **P2（not urgent）**：必ず修正する。ただし、この PR のスコープから外れる場合は、修正を見送ってよい。見送るときは、その旨を報告に含めるか、該当箇所のコードにコメント（見送った理由と、本来どう直すべきか）を書く。

「差分外の既存の問題」として報告されたものは、この PR では修正しない。P0 のものがあれば止めて報告し、P1 と P2 のものは完了時または止めたときの報告に含める。検査できなかった観点があると報告された場合は、その観点を自分で検査してから次に進む。

### 2. 次に進む先を決める

- P0 または P1 で要判断の印が付いた指摘が 1 件でもあれば、修正もマージもせずに止めて報告する。
- P2 で要判断の印が付いた指摘は、この PR のスコープから外れるなら見送って報告に含めてよい。スコープ内なら止めて報告する。
- 修正する指摘（P0、P1、見送らない P2。前回までに見送り済みの P2 のうち、重大さを付け直されていないものは除く）も、見送りのために書くコメントもなければ、手順 4 へ進む。
- どちらかがあれば手順 3 へ進む。

### 3. 修正する

P0、P1 の指摘をすべて直し、P2 の指摘は直すか、手順 1 のとおりに見送る。

- 直し方が衝突する指摘は、重大さの高いほう（特に P0）を優先し、それと両立する形でほかの指摘を直す。両立できない低いほうの指摘は、理由を記録して見送る（P1 を見送る必要がある場合は、要判断として止めて報告する）。
- P2 を見送るためにコードへコメントを書いた場合は、それも修正の一部としてコミットする。
- 修正後、プロジェクトのテスト・型チェック・リントを実行し、通ることを確かめる。
- コミットしてプッシュし、手順 1 に戻る。
- レビューと修正の繰り返しは最大 3 回とする。3 回目の修正の後のレビューでも、P0 または P1 の指摘か、見送りの記録がない P2 の指摘が残る場合は止めて報告する。

### 4. CI を待つ

`gh pr checks --watch` で完了を待つ。

- 失敗したら原因を調べ、修正してプッシュし、手順 1 に戻る。この修正も手順 3 の回数に含める。
- 失敗の原因がこの PR の変更と無関係（不安定なテスト、インフラ障害など）と判断できる場合は、再実行を 1 回だけ試す。それでも失敗すれば止めて報告する。

### 5. マージする

すべてのチェックが通り、P0 と P1 の指摘が残っておらず、P2 の指摘がすべて修正済みか見送りの記録済みであればマージする。

- マージ方式はリポジトリで許可されている方式に従う。指定がなければ squash とする（`gh pr merge --squash`）。
- コンフリクトが機械的に解決できる場合は解消してプッシュし、手順 1 に戻る。解決に判断が要る場合は止めて報告する。
- ブランチ保護で人の承認が必要な場合は、マージを試みずに止めて報告する。

## 止めて報告する場合

次のどれかにあたるときは、それ以上進めずにユーザーに報告する。

- P0 または P1、あるいはスコープ内の P2 で要判断の印が付いた指摘がある。
- P0 と衝突して P1 を見送る必要がある。
- 差分外の既存の問題に P0 のものがある。
- 繰り返しの上限に達した。
- CI の失敗を解消できない。
- 人の承認が必要、または解決に判断を要するコンフリクトがある。
- 履歴の書き換え（force push）やブランチ・データの削除など、取り消しにくい操作が必要になる。

報告には、PR の URL、残っている指摘とその重大さ、止めた理由、ユーザーに決めてほしいことを含める。

## 完了時の報告

マージしたら、PR の URL、レビューと修正を繰り返した回数、直した指摘の要約（重大さごと）、見送った P2 の指摘とその理由（コードにコメントを書いた場合はその場所）を簡潔に報告する。
